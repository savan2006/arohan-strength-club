# Architecture and engineering conventions

## Boundary map

```text
Browser (Next.js)
  ├── Public routes: landing, login, registration
  ├── Member workspace: dashboard, workouts, exercise index, attendance, consistency, membership, profile
  ├── Trainer workspace: roster, reusable workout plans, assignment
  └── Admin workspace: users/roles, membership plans, operating hours, closures
            │ JSON + bearer JWT; CORS allowlist
            ▼
Spring MVC controllers → validated DTOs → transactional services → Spring Data repositories → PostgreSQL
                                              └── Flyway owns schema versioning
```

The frontend does not connect directly to PostgreSQL. The API owns authorization and all business invariants; hiding a button in the UI is not considered authorization.

## Backend package responsibilities

- `controller/`: route mappings, HTTP contracts and authenticated principal hand-off. Keep domain decisions out of controllers.
- `dto/`: request validation and stable response records. Do not serialize JPA entities directly.
- `service/`: use cases, transaction boundaries and domain rules.
- `repository/`: persistence queries only.
- `entity/`: JPA mappings and relationships; enums are in `entity/enums/`.
- `config/`: security chain, JWT encoder/decoder, password encoder and CORS.
- `security/`: issuing JWTs and resolving the current account.
- `exception/`: business/not-found exceptions plus a consistent error response mapper.

Naming uses singular entity names, plural table names, request/response DTO suffixes, descriptive route segments and one responsibility per service.

## Access-control model

| Endpoint family | Access |
| --- | --- |
| `GET /api/health`, `GET /api/gym/status`, `GET /api/membership-plans`, `POST /api/auth/register`, `POST /api/auth/login` | Public |
| `GET /api/auth/me` | Authenticated user |
| `/api/member/**` | `MEMBER` role |
| `/api/trainer/**` | `TRAINER` or `ADMIN` role; service methods still restrict trainer-owned templates and assigned trainees |
| `/api/admin/**` | `ADMIN` role |
| Other `/api/**` | Authenticated by default |

JWTs contain an account subject, user id, role, issue time, expiry and display name. Passwords are encoded with BCrypt. The API refuses a placeholder/development JWT key at startup. Never trust a role sent in a request body; the role claim comes from the signed token.

## Persistence and concurrency

- Flyway migrations under `src/main/resources/db/migration` are the source of truth.
- Hibernate uses `ddl-auto: validate`; it must not silently mutate deployed schemas.
- UUID identifiers are generated by Hibernate.
- `open-in-view` is disabled; service methods map entities to DTOs while the transaction/session is active.
- Foreign keys encode ownership and cleanup for profile, attendance and workout child records.
- A partial unique index enforces one active/completed attendance record per user and facility date, even if requests race. Business validation improves the user-facing error; the database constraint is the final concurrency guard.
- Cross-tab/device change markers are stored in PostgreSQL with a 30-day retention policy; the API returns only change categories relevant to the authenticated account and suppresses events from the same browser tab.
- Neon connection pooling is limited through HikariCP variables. Tune them against the chosen Neon compute size and expected concurrency; don't blindly raise the pool size.

## Frontend conventions

- App Router pages are kept in `src/app`.
- Reusable visual elements and role dashboards are in `src/components`.
- API address/session/error/date/currency utilities are in `src/lib/api.ts`.
- Bearer tokens are held in `sessionStorage`, not persistent `localStorage`; closing the tab clears the token. For higher assurance, consider a server-side backend-for-frontend and `HttpOnly`, `Secure`, `SameSite` cookies before production.
- The interface is responsive and keyboard-aware, and uses reduced-motion preferences. The brand palette is black, red, and warm off-white, not a generic gradient-card template.

## Payments

Fitness-level promotions are calculated from completed calendar-month attendance consistency on the server and written to an audit table; client profile updates cannot directly assign the current level. The weekly plan editor updates only the seven-day plan shape and does not rewrite already-recorded attendance snapshots.

The current membership purchase path creates an explicitly demo/simulated `COMPLETED` payment record so the membership workflow can be exercised locally. Do not use it for real revenue. A production payment design should create a pending order, initiate a provider checkout, verify signed webhooks server-side, handle retries/idempotency and only activate membership after a verified success event.
